## Blocked / needs a human

1. **`lerobot-train` exits 1 at every checkpoint save on Windows:** `OSError: [WinError 1314] A required privilege is not
   held by the client: '000300' -> '...\checkpoints\last'`. Cause: `update_last_checkpoint` makes a symlink, which needs
   admin rights or Developer Mode. The checkpoint itself is written first and is fine. A long run dies at its first
   `--save_freq`. Options: enable Developer Mode (a system setting; I did not touch it), or an in-repo wrapper that
   patches `update_last_checkpoint`. Your call.
2. **torchcodec 0.11.1 can't load:** `RuntimeError: Could not load libtorchcodec ... We support versions 4, 5, 6, 7,
   and 8` / `Could not find module '...libtorchcodec_core8.dll'`. The system FFmpeg is the static WinGet 9.0 build. The
   workaround in use is LeRobot's own `video_backend="pyav"` (PyAV bundles FFmpeg), passed everywhere a dataset is
   loaded or trained. `lerobot-info` still crashes on this. Proper fix: a shared FFmpeg 7/8 on PATH (an install, so
   your call).
3. **pydantic is present only through `wandb`.** `demo_pipeline` needs pydantic, but lerobot doesn't depend on it, and
   the repo goes in with `--no-deps`. With only `lerobot[dataset]` installed:
   `ModuleNotFoundError: No module named 'pydantic'`. It works today because `lerobot[training]` → `wandb` →
   `pydantic 2.14.1`. Recommendation: add `pydantic` explicitly to the lerobot venv recipe.

## Decisions I made

- **Installed `lerobot[dataset,training]==0.6.1`, not bare `lerobot`.** The bare package has no dataset stack, and
  `lerobot-train` needs `accelerate`. I counted lerobot's own extras as "lerobot". I installed nothing outside the
  approved list directly; pydantic arrived as a transitive dependency.
- **Images are stored as `video` (MP4 via PyAV)**, matching spec 8.7 ("front and wrist video"). Feature names are
  `observation.images.<camera>` for each camera in `meta.cameras`, so `front` and `wrist` as the plan says.
- **Passports go to `<dataset>/passports.jsonl`**, one row per episode: `{episode_index, demo_id, passport}`.
  `save_episode(episode_data=None, parallel_encoding=True)` has no custom metadata parameter in 0.6.1.
- **`export_episodes` validates everything before writing.** It needs equal camera sets and `meta.fps == fps` for every
  episode. The output root must not exist yet, because `LeRobotDataset.create` uses `mkdir(exist_ok=False)`. State
  and action are cast to float32.
- **Exporter tests start with `pytest.importorskip("lerobot")`.** Without it, the repo-wide `pytest` in the SANT venv
  collects `lerobot_tools/tests`, fails to import, and aborts the whole run. That would have hidden the 54/165
  baseline.
- **`train_smoke.py` runs the stock `lerobot-train` CLI** in a subprocess, not a patched copy, so the result answers
  "does LeRobot train on Windows" honestly. It enforces the sprint GPU budget (`--steps ≤ 300`, `--batch-size ≤ 8`)
  and writes everything under git-ignored `data/runs/`.
- **No unit tests for `train_smoke.py`.** The plan lists no test file for Task 3, and the run itself is the
  verification. One bug was found that way: the first steps/s figure (7.52) averaged in the warmup window and the loss
  regex matched `kld_loss`. I fixed this in `parse_train_log` and re-checked it against the same `train.log`
  (20.7 steps/s, which matches tqdm's 20.6). I did not use the GPU for a second run.
- **Peak VRAM:** I report lerobot's own torch peak (`mem_gb` 0.99). The whole-GPU nvidia-smi peak was 7184 MiB, but
  Isaac shared the GPU, and per-process numbers aren't available under WDDM.

## 2026-10-16 — Task 2 done: policy server + stdlib client — `0ae1507`

- **Server** `lerobot_tools/policy_server.py --checkpoint <dir> --port 8765 [--device cuda|cpu]` (lerobot venv).
  `<dir>` may be a `pretrained_model/` dir, a step dir, or a run output dir (resolved through `last.txt`). Loads any
  policy type (`PreTrainedConfig.from_pretrained` → `get_policy_class(type)`) plus its saved pre/post-processors.
  State size and camera names/sizes come from the checkpoint config, and `/health` reports them.
- **Choice: stdlib `ThreadingHTTPServer`, not FastAPI/websockets.** Nothing new to install in the lerobot venv, and
  HTTP/JSON matches the plan's routes. Requests are serialized with a lock, because the policy is stateful
  (ACT keeps an action queue).
- **Errors never kill the server:** bad JSON, wrong state length, missing camera, wrong h/w, bad base64, or wrong
  byte count → **400** with the reason; unknown route → 404; policy exception or non-finite action → **500** with
  the message, and the next request still works (tested).
- **Client** `lerobot_tools/policy_client.py`: imports only stdlib + numpy (`PolicyClient(url).health()/reset()/act()`;
  `PolicyServerError` with `.status`, `None` if unreachable). It checks images are HxWx3 uint8 of one size before
  sending. `python -m lerobot_tools.policy_client --url ... --bench 50` measures latency on a live server.
  The task text sent to the policy is `demo_pipeline.rules.TASK_TEXT`.
- **Tests** `test_policy_server.py`: 10 protocol tests against a fake runner (run in both venvs), plus 1 real test:
  the sprint-1 smoke checkpoint (`000300`) over HTTP → finite (9,) actions, 30 calls. SANT `uv run pytest -q`:
  **54 failed, 303 passed, 6 skipped**. Lerobot venv `lerobot_tools/tests`: **29 passed, 2 skipped** (GPU-gated).
- **Latency** (localhost, 2 cameras at 128×128, sprint-1 ACT checkpoint, GPU shared with Terminal 2):

  | Device | queue pop (median / p95) | full inference, after `/reset` (median / p95) | first call |
  |---|---|---|---|
  | cuda | 6.4 / 14.5 ms | **35.9 / 38.8 ms** | ~1.8 s (warmup) |
  | cpu | 6.8 / 7.7 ms | **56.6 / 61.9 ms** | — |

  This ACT config has `chunk_size = n_action_steps = 100`, so a full inference happens once every 100 steps (2 s
  at 50 Hz). The other 99 calls return queued actions (~6.5 ms, mostly HTTP + base64). For sim eval this is fine,
  because the sim waits for the action. Do one warmup `/act` before timing an episode.

## 2026-10-16 — Step 1 done: pure parts (scenes, results, registry) — `50e204e`

- `sim_eval/scenes.py` — `eval_scenes(n, seed0=5000, robot="franka")`: scene i =
  `sample_scene(default_rng(seed0 + i), robot, seed0 + i)`. **Each scene has its own RNG**, so scene 5003 is the same
  whether you run `--n 3` or `--n 50` (tested). Seeds below 5000 are refused (`EVAL_SEED_MIN`), so a test scene
  can never be a training scene (T2 uses seeds 0–49 and 100+).
- `sim_eval/results.py` — `EpisodeResult(seed, success, reasons, ended_by, steps, sim_s, wall_s, error,
  final_cube_pos)`. `ended_by` ∈ `success | time_limit | policy_error | sim_error`. It must be self-consistent:
  a failure needs at least one reason, a success has none. `aggregate()` → `EvalSummary(n, successes, success_rate,
  reasons{code: episodes}, ended_by{...}, mean_wall_s, mean_steps, seeds)`.
- `sim_eval/registry.py` — `update_registry(registry, cell, summary, seed0=, checkpoint=None, results_file=None)`:
  - sets `eval_success = successes / n` (a float, the chart's y value), plus an `eval` record (n, successes,
    seed0, reasons, ended_by, results_file, evaluated_at) on the matching row;
  - **matching:** cell name equal, training `status == "ok"`, and, if given, the checkpoint path equal after
    `resolve()`;
  - **errors instead of guesses:** no match → `LookupError`; several rows for one cell (reruns) without a checkpoint
    → `ValueError`;
  - other lines are kept byte for byte; tmp + `os.replace`;
