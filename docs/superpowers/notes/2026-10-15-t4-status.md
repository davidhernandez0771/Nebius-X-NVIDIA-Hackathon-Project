## Decisions

- **Fixture.** The TS test asserts that its output equals the committed
  `__fixtures__/hand_pose_msg.json`; the test never writes it.
  - The fixture values were computed independently with a node one-liner from the same fixed
    landmarks, not by running `toHandPoseMsg`.
  - Change the fixture deliberately, together with both sides.
- **`wrist_uv` at the image edge.** MediaPipe landmarks can fall slightly outside [0, 1].
  - The TS builder clamps `wrist_uv` to [0, 1]. The Python model rejects out-of-range values
    as the plan says, so edge hands are clamped, not dropped by the relay.
- **Degenerate hands.** A zero-width palm or a NaN landmark becomes `tracking_ok: false`
  (last values kept) in TS. Otherwise the backend would reject it, since palm must be > 0
  while tracking.
- **`HandPoseMsg` strictness.**
  - `extra="forbid"`; NaN and inf are rejected.
  - `yaw_rad` must lie in [−π, π]; `frame_w` and `frame_h` must be > 0; `t_ms` ≥ 0.
  - `palm_width` and `pinch_ratio` must be ≥ 0, and palm > 0 only when `tracking_ok`.
  - `wrist_uv` must lie in [0, 1] always: stale values were valid, and 0 is valid.
- **`Calibration`** validates that every (min, max) pair is ordered.
- **`GripperLatch`** thresholds are constructor arguments (defaults 0.35 / 0.45). It holds on
  `tracking_ok: false` whatever the stale pinch says.
- **Relay.**
  - It accepts, then closes, with **4409** for a duplicate role and **4400** for an unknown role
    (the 4400 code is my choice).
  - The validation error `detail` is pydantic's `str(ValidationError)`.
  - A send failure to a vanishing sim is swallowed, and its handler reports the disconnect.
  - The sim socket's incoming messages are read and ignored, for now.
  - `GET /teleop/status` is exactly as in the plan, without the app's usual `/api` prefix.
    There is no Vite proxy, so the frontend must call the backend origin directly
    (CORS allows `localhost:5173` for HTTP).
- **Throttle (TS).**
  - `MIN_INTERVAL_MS = 33`: a frame is sent if at least 33 ms passed since the last send.
    I chose 33, not 33.3, so a 30 fps camera with jitter is not halved to 15 Hz; the worst
    case is about 30.3 messages per second.
  - Untracked messages also need at least 200 ms since the last untracked send. The first
    loss goes out at once, so the sim's latch holds promptly.
  - Messages are dropped, not queued, while the socket is not open.
- **`TeleopClient`.**
  - `constructor(url, WebSocketImpl = WebSocket)`; the second argument is injectable for tests.
  - `onStatus(cb)` returns an unsubscribe and reports `{socketOpen, simConnected, lastError}`.

  - **Safe ids.** An id is a folder name, so it must match `[A-Za-z0-9_-]+`. Any other id is

    `parent_id` cycle raises `ValueError`.

    `nemotron`, `rules` or `none` (`ValueError` otherwise).

    a duplicate POST.
  - **Corrupt files.** `get_demo` raises pydantic's `ValidationError` (a `ValueError`) for a
    corrupt `demo.json`. `list_demos` skips unreadable or corrupt demos with a log warning,
    so one bad folder does not break the list.
  - **Newest first** means `created_at` descending, then id descending as a tie-break.
  - **Atomic writes:** `tempfile.mkstemp` in the same folder, then `os.replace`. On failure
    the temp file is removed and the old file is left intact (tested).
- **Purity:** stdlib + pydantic only.

## What changed

**Prompt** (`build_diagnosis_prompt`):
- "Find what makes this demo a poor training example" (it presumed a problem) became
  "Decide whether this demo is a good training example as recorded".
- It now says that a clean demo is common and must be `keep` with `"issues": []` and

- **Normal ranges, from the rules' constants and the smoke_cam measurements:**

  - **normal motion:** 0.07–0.26 m/s; single windows dip to about 0.03 m/s at the grasp,

- The jitter example's evidence was "jerk_rms 5x the others" (≈5, which is smooth). It is now
  "jerk_rms 85 vs about 2 elsewhere", consistent with the threshold.

**Gate** (`gate_diagnosis(diag, windows) -> (Diagnosis, list[str])`, run inside `diagnose()`
after parsing):
- **Which windows count:**
  - A range issue is judged on the windows it overlaps by more than an endpoint.
  - A point issue (`t`) is judged on the window(s) containing `t`.
  - An issue with no overlapping window is dropped (no evidence).
- **When each type is dropped:**
  - `rim_contact`: no `contact_arm_bin` in any overlapping window.
  - `jitter`: every overlapping window's jerk_rms is below `JITTER_MIN_JERK`.
  - `slow`: the overlapping windows' median speed is not below `SLOW_SPEED`.
  - All other issue types pass through untouched.
- **Repairs:** a repair is dropped when it overlaps a dropped issue and no kept one.
  - Example: a `remove_pause` that also covers a kept pause stays.
  - Repairs without times (`discard`) are never tied to an issue.
- **Decision:** if the gate drops issues and none remain, the decision becomes `keep` and
  leftover repairs are cleared, each listed. This applies even to a `discard` whose only
  issues were false.
  - A diagnosis the gate dropped nothing from is returned unchanged, even an odd one (e.g.
    `discard` with no issues): that is not the gate's call.
- **Logging:** each dropped item is one line: `dropped issue rim_contact 6.00-6.50: no arm-bin
  contact (B) in any overlapping window`.

**API:**
- `diagnose()` keeps its signature and return type; `diagnose_gated()` also returns the list.
- `POST /demos/{id}/diagnose` and `GET /demos/{id}/diagnosis` now return
  `{source, model_id, diagnosis, gated}`.
- **Gated list storage:** it is saved as `<demo>/gated.json` beside `diagnosis.json`, through
  the store's atomic writer.
  - It is rewritten on every diagnose (`[]` for a rules fallback), so no stale list survives.
  - A missing file reads as `[]`; a corrupt one is a 422.

## Decisions and their reasons

- **`SLOW_SPEED = 5 × STILL_SPEED = 0.05 m/s`**, defined in `diagnose.py` because `rules.py`
  has no slow threshold and is not mine to edit.
  - It is about a third of the clean expert's median window speed (0.135 m/s).
  - Human teleop is naturally slower than the scripted expert. "Slow" should mean a span
    worth retiming (~3× slower), not "slower than a robot script".
  - It is above `STILL_SPEED`, so a real pause also counts as slow.
  - On smoke_cam the two false "slow" spans had medians of 0.108 and 0.170 m/s, both well clear.
  - **Trade-off:** a uniformly 2× slower demo (median ~0.07 m/s) is not flagged slow.
    Lowering recall here is deliberate, to stop false repairs.
- **`rim_contact` is gated on `contact_arm_bin` only.** `MetricsWindow` has no force column,
  and the recorded `max_contact_force` covers only arm-vs-bin/table contacts, so B is the
  evidence.
  - **Gap:** a *cube*-on-rim contact is not recorded at all (the signals have no cube-bin
    contact). The gate would therefore drop a real cube-rim hit that the model saw in the
    images.
  - **For T2:** add a `contact_cube_bin` signal if that case matters.
- **`drop` is not gated.** The task listed rim_contact, jitter and slow. The prompt rule covers
  `drop`, and a wrong gate could hide a real drop.
- **`gated.json` is a sidecar written by the router** because `store.py` was outside this
  task's file list. It reaches the folder via `store.episode_dir(id).parent` and imports the
  store's private `_write_atomic`.
  - **Lead:** move it into `StoredDiagnosis.gated` (default `[]`) and drop the sidecar.

## Limits, honestly

- **This is n = 1, one sample.** One clean episode, one call. The model's output varies run to
  run, so "0 issues" here does not prove a clean-demo false-positive rate of 0. The offline
  gate check is deterministic, though: it removes all 5 original false positives.
- **Recall is unmeasured.** The calibrated prompt says "when in doubt, leave it out", and the
  gate removes issues. Both could now hide real problems.
  - **Next:** run `diagnose_gated` on rendered *degraded* episodes (T1's `degrade` + T2's
    replay with cameras). Score them with T1's `score_diagnosis` against the
    `InjectedIssue` ground truth, and compare with the rules baseline.
  - This needs real frames of degraded demos, which no track has produced yet.
- **The normal ranges come from one scripted Franka episode.** Re-measure them on human
  teleop episodes (and OpenArm) once those exist.
